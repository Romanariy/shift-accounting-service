# Shift Accounting Service

## Свод: услуги, расходы и счета

Главная страница — новое рабочее пространство с обзором, журналом работ, расходами,
счетами, услугами и настройками. Сервер остаётся на Django/PostgreSQL, интерфейс —
Next.js. Приложение разворачивается существующим Docker Compose; оно не является
Cloudflare Worker и не публикуется непосредственно на хостинге Sites.

Журнал открывается по месяцам. Поиск, фильтры организации, сотрудника, услуги, вида
работы, статуса и источника применяются ко всему выбранному месяцу до разбиения
на страницы. Сортировка доступна через заголовки колонок и список вариантов.
Кнопки изменения, истории и удаления имеют подсказки при наведении и фокусе.

### Обновление и первый запуск

Миграция `ledger.0003_daily_calculation` добавляет дневные расчёты без изменения
исторических сумм. Перед обновлением остановите пишущие процессы и сделайте копию БД.
Старые почасовые записи переводятся через «Предпросмотр пересчёта»: проверьте доли
каждого участника и подтвердите применение. До перевода добавить часть к такой
исторической смене нельзя. Подтверждённые счета этот пересчёт пропускает.

Записи одной почасовой услуги в одной организации за один день имеют общий минимум и максимум.
Общая сумма распределяется по часам между всеми записями, включая несколько записей
одного сотрудника. Ставка и пределы сохраняются в снимке дневного расчёта; изменение
тарифа применяется к существующей группе только через явный пересчёт. Фиксированные
услуги и сопровождения рассчитываются отдельно за каждую запись.

Комментарии типовых услуг в боте пишутся после организации:
`12.04 10:00–14:00 Фокус подменил коллегу + 2 сопр задержались`.
Без явной организации бот использует организацию услуги по умолчанию, а остаток
сохраняет как комментарий. В комментариях типовых услуг буквальный плюс записывается
как `\+`; обычный `+` начинает следующую услугу. У разовых работ и расходов `+`
остаётся частью описания. Изменение только комментария не пересчитывает суммы.

Проверки конкурентной записи требуют PostgreSQL:
`python manage.py test apps.ledger.test_shared_concurrency`.
На SQLite эти два теста пропускаются; остальные тесты расчёта, миграций и парсера
выполняются на обеих базах. Тестовая БД создаётся отдельно от рабочей.

1. Сделайте резервную копию рабочей БД. Выполните `python manage.py migrate`.
2. В «Услуги и тарифы» проверьте перенесённые тарифы организаций. Укажите организацию
   по умолчанию для сопровождений. Для телефонов задайте фиксированный тариф и
   ежедневное автоначисление с организацией и датой начала.
3. В «Настройки → Telegram и расписание» укажите Chat ID и ID топиков услуг и расходов.
   Пустой ID топика означает всю указанную группу; пересекающиеся маршруты запрещены.
   Без настройки топика сообщения этой группы не учитываются.
4. Запустите бота. Получатели и утверждающий должны написать ему `/start` в личном чате.
   Затем назначьте их на сайте. Настройте Telegram ID и алиасы сотрудников.
5. Проверьте первый пакет на сайте: период, организации, Excel, состав, корректировки.
   После этого можно включить ежемесячную подготовку. По умолчанию она выключена.

В Docker профиль `bot` запускает и бота, и новый процесс `billing`. Отдельный запуск:

```powershell
python manage.py run_shift_bot
python manage.py run_billing_worker
```

`run_billing_worker --once` выполняет один цикл, включая доставку уже поставленных
в очередь сообщений. Не используйте его для пробного запуска с реальным токеном.
Без `TELEGRAM_BOT_TOKEN` worker выполняет только начисления и подготовку.
Секреты остаются в окружении. Настройки получателей и расписания хранятся в БД.
Для метаданных фронтенда задайте `SITE_URL` равным доверенному адресу вашего сайта.

### Форматы сообщений

Типовые услуги, общий день, независимые организации:

```text
12.04 10:00–14:00 Фокус + 2 сопр
2 сопр
Уборка Фокус
```

Каждая часть использует явно указанную организацию либо настройку своей услуги.
Организация соседней части не наследуется. Автоматические услуги не принимаются
как ручные сообщения, чтобы не дублировать ежедневные/ежемесячные начисления.

Разовая работа, с исполнителем или от автора сообщения:

```text
Рамис, 12.04, 1500, Починил дверь, Фокус
12.04, 1500,50, Починил дверь, замок + ручку, Фокус
```

Описание может содержать запятые и `+`. Дата, сумма, описание и организация обязательны.
Неизвестный исполнитель требует проверки; запись не создаёт новую типовую услугу.

Расходы в отдельном топике:

```text
Краска, 1500, Фокус
12.04, Краска, кисти, 1500,50, Фокус
```

Без даты используется дата сообщения в `DJANGO_TIME_ZONE`. Повторная доставка
Telegram update не создаёт новые записи. Редактирование сообщения обновляет его
записи целиком; ошибка в одной части отменяет всё изменение. Удалять записи нужно
на сайте. После включения в подтверждённый счёт изменение требует явной корректировки
на сайте и подготовки новой версии счёта.

### Отчёты и подтверждение

Каждая организация получает свой Excel. Первый лист «Основной» содержит общую сводку,
услуги без отдельного листа и все разовые работы. Другие услуги группируются по
настроенному листу; расходы — на «Расходы». Детализация не дублируется между листами.
Доплаты и скидки требуют пояснения. Формулы из введённого пользователем текста
экранируются; итоговые значения сохраняются численно.

Все неудалённые записи организации, включая услуги, разовые работы и расходы,
учитываются в новых счетах автоматически. Ручные флажки включения и исключения
убраны. Старые флаги в БД оставлены для совместимости, но при подготовке нового
счёта игнорируются; уже подтверждённые файлы не пересчитываются. Это правило
действует и для записей с пометкой `[ТЕСТ]`.

Пакет готовится вручную или 1-го числа в 10:00 по Екатеринбургу за прошлый месяц.
Утверждающему сначала отправляются все файлы, затем общая сводка и кнопки. Подтвердить
в боте может только назначенный пользователь по Telegram ID. Если данные изменились,
пакет обновляется и требует повторного подтверждения. Подтверждённые файлы хранятся
в БД вместе со снимками строк и получателями, а не пересоздаются из текущих записей.

Перед отправкой блокируются непроверенные записи, отсутствующие тарифы и получатели.
Пустые счета не отправляются. Пересекающиеся подтверждённые периоды требуют создания
новой версии. При сбое обработчика доставка со статусом «Отправляется» через пять минут
переходит в «Нужно проверить доставку»: Telegram мог принять сообщение до обрыва связи.
Автоматического повтора такой доставки нет. Проверьте чат и подтвердите повтор на сайте.
Ошибки Telegram и результат доставки показываются отдельно для каждого получателя.

На сайте можно полностью удалить отдельный счёт или весь пакет. Удаляются файл,
снимок счёта и задания доставки, исходные работы сохраняются. Сообщения и Excel,
уже доставленные в Telegram, остаются у получателя. Пока выполняется отправка,
удаление заблокировано до получения результата. Удалённый плановый пакет не
создаётся автоматически повторно в том же месяце; его можно подготовить вручную.

### Перенос и совместимость

Миграции `ledger.0001` и `ledger.0002` добавляют новые таблицы и копируют исторические
смены/сопровождения с сохранением сумм и ссылок на старые записи. Старые таблицы и
история не удаляются. Исторические общие телефоны за прошедшие дни начиная с месяца
первой смены фиксируются отдельно без организации и исключаются из счетов, пока
администратор их не распределит. Новые телефоны не включаются автоматически.

Смена или сопровождение нового журнала зеркалируется в прежний формат для внешней
синхронизации. Разовые услуги, расходы и другие новые услуги не отправляются во внешнюю
БД без нового контракта. Старые API и экспорт остаются для совместимости; для новых
счетов и фиксированных телефонов используйте новое рабочее пространство.

Новые API находятся под `/api/shifts/ledger/`: `bootstrap`, `services`, `rates`,
`accruals`, `preferences`, `organizations`, `contacts`, `settings`, `records`,
`recalculate`, `batches`, `invoices`, `deliveries`, `audit`.
Действия: `POST batches/<id>/approve/` с `version`, `POST batches/<id>/refresh/`,
`GET invoices/<id>/file/`, `PUT invoices/<id>/` с корректировками,
`DELETE invoices/<id>/`, `DELETE batches/<id>/`,
`POST deliveries/<id>/retry/`. Пересчёт сначала возвращает изменения и fingerprint;
применение требует того же fingerprint. Денежные суммы передаются строками.

Журнал: `GET records/?month=2026-09&kind=work&status=review&ordering=-amount`.
Дополнительные параметры: `organization`, `employee`, `service`, `source`, `q`,
`offset`, `limit` (по умолчанию 50, максимум 250). Для `employee` и `organization`
поддерживается `unassigned`. Фильтры пакетов: `month`, `organization`, `state`;
сортировка пакетов — `ordering=id` либо `ordering=-id`.

Доступ к приложению и API в рабочем развёртывании по-прежнему защищает Caddy Basic Auth;
не публикуйте внутренний порт Django напрямую. Сайт не является кабинетом владельца:
владельцы получают только собственные файлы через бота.

Проверки:

```powershell
python manage.py test apps.ledger apps.shifts
python manage.py check
python manage.py makemigrations --check --dry-run
```

Во `frontend`: `npm run build`. Тесты не используют реальный Telegram: отправитель
подменён, миграция истории проверяется на отдельной временной БД.

## Предыдущий интерфейс и совместимые API

Отдельный сервис для учета смен, сопровождений, оплат и Excel-отчетов.

## Возможности

- Telegram-бот читает сообщения из группы или конкретного топика.
- Дата необязательна: без неё используется сегодняшний день в `DJANGO_TIME_ZONE` (по умолчанию Екатеринбург). В конце обязательно название организации или её алиас.
- Примеры: `10:00-16:00 фокус`, `01.04 10:00-16:00 + 2 сопр фотобар`, `Уборка к`, `Покраска циклораммы квин`, `+ 2 сопр фотобар`.
- Ручное назначение автора: `Рамис 01.04 10:00-16:00 фокус` или `01.04 Наташа 10:00-16:00 квин`.
- Требуются время, вид работы или положительное количество сопровождений; `привет фокус` не создаёт запись. Только сопровождения не создают пустую смену.
- История изменений для записей, сотрудников и правил оплаты.
- Справочники сотрудников, организаций (названия, алиасы, активность и лист Excel) и стоимости оплаты.
- Тариф смены определяется организацией, типом работы и датой. Большой/малый админ, уборка и покраска настраиваются отдельно для каждой организации. Сопровождения и телефоны используют общие тарифы.
- Excel: смены Фокуса и Фотобара первоначально на листе `Фокус и Фотобар`, Квина — на `Квин`; `Сопровождения` и `Телефоны` общие. Одинаковый лист в настройках объединяет организации, в том числе при экспорте прошлых месяцев.
- Очередь синхронизации с глобальной БД после новых данных и по расписанию.

## Backend

После обновления выполнить `python manage.py migrate`. Миграция `0002_organizations` создаёт организации и независимые копии существующих общих тарифов для каждой из них. Если правил нет, используются исходные ставки: большой админ 1400 ₽, малый 200 ₽/час (600–1200 ₽), уборка 700 ₽, покраска 1000 ₽. Новая организация получает копию расписания тарифов Фокуса.

Тип работы «Фотобар» удалён: старые смены и настройки сотрудников переводятся в «Малый админ» без изменения сохранённых сумм, прежние тарифы архивируются в истории. Старые записи остаются без организации и могут быть исправлены вручную; такие смены экспортируются на лист `Без организации`. Для их редактирования сохранены общие тарифы. Изменение тарифа не пересчитывает записи автоматически; сохранение отредактированной смены пересчитывает её по действующему на дату тарифу. При отсутствии тарифа сохранение отклоняется.

Миграция переноса данных необратима средствами Django: перед обновлением рабочей базы сделайте резервную копию. Отключение организации сохраняет её историю и отчёты, но исключает её из новых записей.

API справочника: `GET/POST /api/shifts/organizations/`, `GET/PUT/DELETE /api/shifts/organizations/<id>/` (`DELETE` отключает организацию). Поля: `name`, `aliases`, `excelSheet`, `isActive`. У записей добавлены `organizationId` и `organizationName`, у тарифов — `organizationId`. Организация обязательна для новых ручных записей и новых тарифов смен; для тарифов сопровождений и телефонов поле должно быть пустым. Новые сообщения очереди синхронизации включают организацию.

Проверки: `python manage.py test apps.shifts`, `python manage.py check`, `python manage.py makemigrations --check --dry-run`; во `frontend` — `npm run build`.

```powershell
cd backend
pip install -r requirements.txt
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver 127.0.0.1:8000
```

Запуск бота:

```powershell
$env:TELEGRAM_BOT_TOKEN="token"
python manage.py run_shift_bot
```

Запуск синхронизации каждый час:

```powershell
$env:SHIFT_SYNC_ENDPOINT="https://example.com/api/sync"
$env:SHIFT_SYNC_TOKEN="secret"
python manage.py sync_shifts --loop --interval 3600
```

## Docker-развертывание на VPS

В Docker-режиме поднимаются:

- `db` — PostgreSQL.
- `backend` — Django + Gunicorn.
- `frontend` — Next.js production server.
- `caddy` — reverse proxy на 80/443.
- `bot` — Telegram-бот, включается профилем `bot`.
- `sync` — фоновая синхронизация, включается профилем `sync`.

### Первый запуск

На сервере установите Docker и Docker Compose plugin, затем положите проект, например в
`/opt/shift-accounting-service`.
Если используете домен, A-запись домена должна смотреть на VPS, а порты `80` и `443`
должны быть открыты в firewall.

```bash
cd /opt/shift-accounting-service
cp .env.example .env
nano .env
```

Минимально поменяйте в `.env`:

```env
APP_DOMAIN=your-domain.example
POSTGRES_PASSWORD=strong-db-password
DJANGO_SECRET_KEY=strong-django-secret-key
DJANGO_ALLOWED_HOSTS=your-domain.example,backend
DJANGO_CSRF_TRUSTED_ORIGINS=https://your-domain.example
DJANGO_SECURE_SSL_REDIRECT=1
TELEGRAM_BOT_TOKEN=123456:telegram-token
DJANGO_API_BASE_URL=http://backend:8000
```

### Защита сайта логином и паролем

Внешний доступ к сайту, админке и API закрыт через Caddy Basic Auth.
Сгенерируйте хэш пароля на VPS:

```bash
docker run --rm --entrypoint caddy caddy:2-alpine hash-password --plaintext 'your-strong-password'
```

Вставьте результат в `.env` в одинарных кавычках:

```env
SITE_BASIC_AUTH_USER=admin
SITE_BASIC_AUTH_PASSWORD_HASH='$2a$14$...'
```

После изменения `.env` пересоздайте Caddy:

```bash
docker compose up -d --force-recreate caddy
```

Теперь браузер будет спрашивать логин и пароль перед открытием сайта.

Если домена пока нет, оставьте:

```env
APP_DOMAIN=:80
DJANGO_ALLOWED_HOSTS=localhost,127.0.0.1,backend
DJANGO_CSRF_TRUSTED_ORIGINS=http://localhost,http://127.0.0.1
DJANGO_SECURE_SSL_REDIRECT=0
```

Запуск сайта и бота:

```bash
docker compose --profile bot up -d --build
```

Создать администратора:

```bash
docker compose exec backend python manage.py createsuperuser
```

Посмотреть логи:

```bash
docker compose logs -f backend
docker compose logs -f frontend
docker compose logs -f bot
```

Остановить:

```bash
docker compose --profile bot down
```

### Обновление на сервере

Лучший вариант — хранить проект в Git-репозитории и обновлять сервер через `git pull`.

```bash
cd /opt/shift-accounting-service
git pull
docker compose --profile bot up -d --build --remove-orphans
docker image prune -f
```

Миграции и сбор статических файлов выполняет сервис `migrate` при каждом `up`.

### Бэкап базы

```bash
mkdir -p backups
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > backups/shift_accounting_$(date +%F_%H-%M).sql
```

Автоматический сжатый бэкап с хранением последних 14 дней:

```bash
sh deploy/backup-db.sh
```

Добавить ежедневный бэкап в cron:

```bash
crontab -e
```

```cron
15 3 * * * cd /opt/shift-accounting-service && sh deploy/backup-db.sh >> backups/backup.log 2>&1
```

Восстановление:

```bash
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" "$POSTGRES_DB"' < backups/file.sql
```

Если бэкап сжатый:

```bash
gzip -dc backups/file.sql.gz | docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" "$POSTGRES_DB"'
```

### Как быстро выгружать проект на сервер

Рекомендуемый путь:

1. Завести приватный GitHub/GitLab репозиторий.
2. На компьютере коммитить изменения.
3. На VPS делать `git pull` и `docker compose --profile bot up -d --build --remove-orphans`.

Если Git пока не нужен, можно копировать через `rsync`:
