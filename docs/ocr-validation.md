## Набор и методика

Использованы все 39 изображений из предоставленного `DS.zip`. Среди них есть повторы,
разные масштабы, баннеры, перекрытия интерфейсом, чёрные тела карточек, сокращённые
названия залов и скрытые начало/окончание. Этот же набор использовался при разработке
правил, поэтому он не является независимой проверкой.

Разметка — `backend/scripts/ds-reference.json`; результаты по каждому изображению,
контрольные суммы, вопросы и измерения — [ocr-development-report.json](ocr-development-report.json).
Имена и телефоны клиентов в этих файлах отсутствуют. Сами фото и веса не входят в git.

Единица основной оценки — один скриншот. Сравниваются организация, дата и **все**
найденные интервалы, а не только минимальное/максимальное время. Профиль Фотобара задан
названиями БОХО, Модерн, INLIGHT, Стол визажный. Для двух других групп скриншотов
организация представлена условным ID семейства залов; реальные названия этих организаций
ещё должен подтвердить пользователь. Поэтому это также не проверка готовых профилей
всех рабочих организаций.

Для воспроизводимости выбора года использована опорная дата `2026-08-24`, перед всеми
датами архива. Это специально исключает обязательные вопросы о прошедшем времени из
измерения качества чтения. При отправке тех же старых фото сейчас вопросов будет больше.
В рабочем процессе прошедшее время не публикуется. Скрытое значение в разметке отмечено
`null`; такое изображение не должно приниматься без уточнения.

При повторной визуальной проверке исправлена разметка изображения №29: весь текст
`17:00–20:00` виден над нижней навигацией, хотя тело карточки скрыто. Это достаточное
основание для чтения окончания по тексту. Изменение разметки документировано в JSON;
результат не выдаётся за оценку на заранее замороженной независимой выборке.

## Измеренные результаты

| Показатель | Результат |
|---|---:|
| Изображений | 39 |
| Без вопросов распознавания | 21 |
| Совпали со всеми проверяемыми полями среди этих 21 | 21 |
| Требуют уточнения | 18 |
| Наблюдаемая точность среди принятых | 100% (21/21) |
| Покрытие без уточнений | **53,85%** |
| Формальная нижняя граница Wilson, 95% | 84,54% |

21 правильный пример не доказывает вероятность правильности выше 99%. Кроме малого
объёма, примеры зависимы и использованы для настройки; поэтому даже приведённая
формальная граница не является валидной оценкой независимого рабочего потока.
Обязательная проверка перед публикацией действует и для этих 21 результатов.
Оценки уверенности самого OCR используются как диагностический сигнал, не как
вероятность правильности всей заявки.

Показательные случаи:

- №24, Фотобар, 12 сентября: найдены чёрная карточка `13:00–16:00` и светлая
  `16:30–?`. Штрихованный блок `13:00–20:00` исключён. Задаётся вопрос об окончании
  второй записи; после ответа `20:00` получается `13:00–20:00`.
- №8: два начала скрыты верхней границей календаря. Наличие полностью видимой третьей
  записи не отменяет вопрос обо всех интервалах.
- №29: узкий заголовок прямо над навигацией теперь включается в анализ; оба времени
  читаются. Прежняя фиксированная нижняя граница пропускала эту запись.
- №37: затемнение поверх даты может скрывать первую цифру, даже при высоком OCR-score;
  требуется подтверждение даты.

Текущий детектор настроен на вертикальный мобильный календарь из примеров. Android,
десктопная версия, тёмная тема, другой масштаб интерфейса и изменённая версия YCLIENTS
требуют отдельной разметки и проверки. Поддержка произвольного оформления не доказана.
Для скрытых исходных данных точность не повышается угадыванием: нужны дополнительный
скриншот или ответ человека. Это ограничивает достижимое покрытие данного архива.

## Скорость, ресурсы и отсутствие сети

Измерено на локальном Windows x64, Python 3.10.9; CPU определён как
`Intel64 Family 6 Model 186 Stepping 2, GenuineIntel`. PaddlePaddle 3.2.0,
PaddleOCR 3.3.2, PaddleX 3.3.13. Указано два потока для OCR, OpenCV и библиотек
вычислений; аппаратное ограничение ровно двумя ядрами не устанавливалось.

| Показатель | Измерение |
|---|---:|
| Инициализация OCR в benchmark | 7,142 с |
| Медиана на скриншот | 1,173 с |
| 95-й процентиль на скриншот | 2,153 с |
| Максимум на скриншот | 2,212 с |
| Максимальная сумма двух соседних обработок | 4,090 с |
| Отдельный реальный прогон двух фото №18 и №20 + объединение | **2,539 с** |
| Максимум RSS среди снятых замеров процесса | 662,1 МиБ |
| Суммарное CPU-время процесса (инициализация, 39 фото, дополнительная пара) | 118,89 с |

Для пары получены три объединённые записи и содержательный вопрос `interval:1:end`,
а не просто сообщение «обрабатывается». Модели уже были загружены. Замер **не включает**
загрузку Telegram, ожидание очереди, сбор альбома (1,5 с), сеть ответа и холодный старт.
RSS замерялся между изображениями и может не включать кратковременный пик внутри inference.
На машине параллельно выполнялись проверки проекта; это локальный ориентир, не SLA.

Во всём прогоне запрещены `socket.connect`, `connect_ex` и `create_connection`.
Все 39 изображений и отдельная пара обработались с этим запретом. В Compose дополнительно
задана внутренняя сеть OCR без внешнего доступа. Фактическая контейнерная сетевая изоляция
и задержка на целевом Linux CPU ещё должны быть проверены на стенде.

## Проверки приложения

- Полный Django-прогон: **177 тестов, 174 прошли, 3 пропущены**, ошибок нет.
  Пропущены проверки конкурентных транзакций, которым нужен PostgreSQL: две существующие
  проверки журнала и новая проверка одновременного взятия предложения. SQLite не
  подтверждает корректность блокировок PostgreSQL.
- 23 теста frontend прошли, включая бинарный multipart/PNG, ограничение размера,
  проверку происхождения запросов и сохранение разрешений профиля.
- Проверка Django и отсутствие недостающих миграций — без ошибок.
- Production-сборка Next.js прошла, включая проверку типов. Структура Compose проверена
  разбором YAML; синтаксис двух новых Linux-скриптов проверен `bash -n` без их выполнения.
- Полный сценарий с имитацией Telegram: приём → OCR → подтверждение → фотографии и
  управляющее сообщение → назначение → личные кнопки → снятие. В журнале не создаются работы.
- Проверены права, устаревшие нажатия, поздние части альбома, дедупликация, восстановление
  OCR, неопределённая доставка, запрет повторной отправки без сверки, версии обновлений,
  повтор окончательно неудавшегося обновления, очистка изображений и подготовка после restore.
- Через браузер на отдельной тестовой БД проверены список, фото, профили залов, вопрос
  о скрытом окончании, пересчёт `13:00–20:00`, запрет публикации прошедшего предложения.
  Реальные сообщения пользователям не отправлялись.
- Разрешение зависимостей для Linux amd64/Python 3.12 выполнено через pip без установки:
  доступны совместимые wheel-пакеты, 84 версии зафиксированы в `requirements-ocr-linux.lock`.
  Это проверка установки зависимостей, а не запуск Linux-кода.

Полный Docker Compose, реальные PostgreSQL-блокировки, рабочий Telegram и восстановление
из резервной копии на Linux **не запускались в этой среде**: Docker/Podman/PostgreSQL
и Linux-подсистема здесь отсутствуют. Подготовлен воспроизводимый сценарий
`deploy/smoke-offers.sh` и ручная проверка в [инструкции](shift-offers.md).

## Воспроизведение OCR-оценки

Из корня проекта в окружении с OCR-зависимостями и локальными весами:

```sh
python backend/scripts/benchmark_offers.py DS.zip --offline --today 2026-08-24
python backend/scripts/evaluate_offers.py .local/ocr-eval/report.json --output docs/ocr-development-report.json
```

В OCR-образе корень приложения — `/app`, скрипты находятся в `scripts/`, веса —
`/opt/ocr/models`; передайте `--models /opt/ocr/models`. Не загружайте архив и фото
в общедоступное хранилище. Benchmark сохраняет извлечённые фото в указанном `--output`.
Эти файлы не относятся к рабочей очереди и не очищаются её политикой хранения.

## Условия для автопубликации

Следующий этап — независимо разметить новые **заявки/альбомы**, заморозить правила,
профили и веса перед проверкой, отделить повторные изображения и снимки одной съёмки
между наборами. Проверять правильность организации, полной даты, всех записей и итогового
диапазона целиком. Отдельно считать долю уточнений, ошибки принятия и задержки при нагрузке.
Для убедительной оценки нужны сотни независимых принятых заявок, а не десятки похожих фото.

Программный барьер требует одновременно `OFFER_AUTO_PUBLISH=1` и отдельный доступный
только для чтения отчёт с совпадающей `engine_version`, `independent=true`,
`split_by_album=true`, `accepted>=300`, `coverage>=0.90`, `lower_precision_95>0.99`.
Числа отчёта должны получаться из независимой проверки, а не вводиться для обхода барьера.
Текущий `ocr-development-report.json` эти условия не выполняет и не включает
автопубликацию. Если появится подтверждающий отчёт, его надо одинаково смонтировать
в backend и recognition; одного изменения переменной окружения недостаточно.
