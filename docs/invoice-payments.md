# Подтверждение оплаты счёта

В разделе «Счета» подтверждение доступно в строке списка и в карточке актуального
подтверждённого счёта, ожидающего оплаты. Перед сохранением показываются организация,
номер, версия и сумма. Подтверждение закрывает ожидание для всех получателей.

Для оплаченного актуального счёта доступна отмена с обязательной причиной.
Она возвращает ожидание оплаты, в том числе после подтверждения через Telegram.
В карточке доступна история с прежней датой, автором и причиной отмены.
Фильтры и открытая карточка сохраняются при обновлении статуса и общего счётчика.
Черновики, заменённые счета и счета без подтверждения оплаты исключены из действий.

## API

Оба действия используют существующий административный доступ сайта:

- `POST /api/shifts/ledger/invoices/<id>/confirm-payment/`
- `POST /api/shifts/ledger/invoices/<id>/cancel-payment/`

Пример подтверждения:

```json
{"version": 1, "payment_revision": 0}
```

Пример отмены после него:

```json
{"version": 1, "payment_revision": 1, "reason": "Ошибочная отметка при сверке"}
```

Версия и ревизия берутся из списка/карточки счёта. Устаревшее действие возвращает
ошибку с просьбой обновить данные. Повтор уже выполненного подтверждения не создаёт
новое событие. Отмена всегда требует текущей ревизии и непустой причины до 2000 символов.
История доступна через существующий `audit/?entity_type=invoice&entity_id=<id>`.

Сайт записывает текущее время и `paid_by=null`, показывая «Администратор сайта».
Telegram сохраняет числовой ID получателя. Изменение статуса, ревизии, история и
задания Telegram сохраняются атомарно под общей блокировкой учёта.
Доставка, Excel, стоимость работ, полученные оплаты и заработок не меняются.

## Telegram

Worker `billing` убирает либо восстанавливает кнопки в уже доставленных сообщениях,
не отправляя документы повторно. Очередь хранит свою ревизию; завершение старого
сетевого запроса не поглощает новое изменение, а запускает сверку текущего состояния.
После перезапуска незавершённое редактирование повторяется. Будущая доставка и
доставка, начавшаяся до изменения оплаты, сверяются с текущей ревизией.

Новые кнопки имеют формат `ledger:paid:<invoice>:<version>:<payment_revision>`.
Прежний формат без ревизии действует до первого изменения оплаты. После отмены
старое нажатие не подтверждает оплату повторно. Недоступность Telegram не откатывает
действие сайта; сохраняется существующий механизм повторов и ошибок очереди.

## Обновление

Миграция `ledger.0013_invoice_payment_revision` добавляет две ревизии с нулевым
начальным значением: у счёта и задания редактирования кнопок. Статусы старых счетов
и финансовые данные не изменяются. Применить миграцию перед запуском нового backend
и фоновых обработчиков. Новых сервисов Compose не требуется.

Изменены образы backend (включая bot и billing) и frontend. OCR-образ не менялся.
Существующий сервис `migrate` выполняет миграции при обновлении через Compose.

## Проверка 10.10.2026

- PostgreSQL 18, отдельная заново созданная тестовая база: **272 теста прошли**,
  включая конкурентное подтверждение сайта/Telegram, конкурентную отмену, устаревшие
  ревизии, гонки очереди, восстановление и последующее удаление кнопки.
- Frontend: **43 теста прошли**, production-сборка Next.js завершилась успешно.
- Миграции применены на тестовых PostgreSQL и SQLite; отсутствуют несозданные миграции.
- Браузер: список, карточка, подтверждение, отмена с причиной, счётчик, сохранение
  карточки и история проверены на отдельной SQLite-базе со своими тестовыми данными.
  Ошибок консоли не обнаружено. Снимки находятся в `output/web-payment-check/`.
- Telegram проверен через тестовый отправитель. Реальная доставка и запуск Linux
  Compose в этой среде не проверялись; Docker CLI отсутствует.

Существующий тест устаревшего изменения поступления стабилизирован явным переводом
тестовых часов на секунду вперёд: быстрые запросы Windows могли иметь одинаковую
дату изменения. Производственная логика поступлений не менялась.
