## Ошибки, которые стоит исправить первыми

P1 — исправить до регулярного использования соответствующего сценария. P2 — исправить следующим этапом. Статус «воспроизведено» означает проверку диагностическим сценарием; «по коду» означает установленную проблему реализации без полного воспроизведения внешней среды.

### F01 · P1 · Типовую услугу нельзя сохранить обычным заполнением формы

**Воспроизведено компонентным и серверным сценариями.** Форма новой услуги содержит необязательное поле «Сумма для ввода готовой стоимости», но всегда отправляет `amount: ""`. Сервер вызывает `money("")` даже для почасового тарифа и возвращает 400 «Некорректная сумма». Пользователь заполняет организацию, исполнителя и 10:00–14:00, но запись не сохраняется.

Контрольный запрос без поля `amount` сохраняет ту же смену и рассчитывает 800 ₽. Ввод `0` также позволяет пройти этот участок проверки, но интерфейс не объясняет такой обход.

Исправление: формировать поля и запрос по типу услуги; готовую сумму требовать только для соответствующего способа расчёта. Сервер должен самостоятельно нормализовать необязательные значения и проверять контракт типа услуги.

Код: [AccountingApp.tsx](../../frontend/src/components/AccountingApp.tsx), строки 110–115; [engine.py](../../backend/apps/ledger/engine.py), строки 125–132. Диагностика: `service_form_blank_amount`, `service_form_defaults`.

### F02 · P1 · Django Admin обходит расчёты, защиту счетов и историю журнала

**Воспроизведено вызовом используемого `ModelAdmin.save_model`.** `Record` зарегистрирован стандартным администратором. Он сохраняет модель напрямую, минуя `save_record` / `commit_records`.

После изменения 4 часов на 8 запись содержит 8 часов, дневная группа продолжает содержать 4 часа, сумма остаётся 800 ₽. Событие в используемый журналом `AuditLog` не добавляется. Обычный Django Admin может отдельно вести свой `LogEntry`, но это не обеспечивает расчёты и историю нового журнала. На этом пути также отсутствует доменная проверка включения записи в подтверждённый счёт.

Глобальная блокировка middleware не решает проблему: она упорядочивает сохранения, но не запускает расчётные правила.

Исправление: сделать расчётные записи в Admin доступными только для чтения либо направить все изменения и удаления через общие доменные операции. Также ограничить редактирование служебных полей `daily_calculation`, `amount`, `auto_key`, `deleted_at`.

Код: [ledger/admin.py](../../backend/apps/ledger/admin.py), строки 2–5; [middleware.py](../../backend/apps/ledger/middleware.py). Диагностика: `admin_bypasses_engine`.

### F03 · P1 · Старое окно редактирования может незаметно вернуть прежнюю сумму

**Воспроизведено через API.** Две вкладки открыли разовую работу на 100 ₽. Первая сохранила 200 ₽. Во второй изменили только комментарий и отправили сохранённые значения формы. Сервер принял запрос с HTTP 200 и вернул сумму к 100 ₽.

`updated_at` передаётся в данных, но не используется как условие обновления. Транзакционная блокировка защищает от одновременной записи, но не распознаёт устаревшую форму.

Исправление: optimistic locking с версией записи / `If-Match` и ответом 409 на конфликт; дополнительно отправлять только изменённые поля. Такой же контроль нужен для списков корректировок и настроек.

Код: [AccountingApp.tsx](../../frontend/src/components/AccountingApp.tsx), строки 115, 125; [engine.py](../../backend/apps/ledger/engine.py), функция `save_record`. Диагностика: `lost_update`.

### F04 · P1 · Успешное сохранение с последующим сбоем загрузки провоцирует дубли

**Воспроизведено компонентным сценарием с имитацией сбоя сети.** `run()` последовательно выполняет запись и `load()` в одном `try`. Если POST уже прошёл, а обновление данных упало, форма остаётся открытой и показывает ошибку. Повторное «Сохранить» выполняет второй POST с идентичным содержимым. Защиты от дубля для ручных записей нет.

В диагностике получены два одинаковых POST. Серверная идемпотентность Telegram здесь не помогает, поскольку ручная запись не имеет `chat_id/message_id`.

Исправление: разделить результат записи и результат обновления экрана; после успешного POST закрывать форму и показывать отдельно ошибку обновления. Для создания работ и пакетов добавить ключ идемпотентности. Обработать и ситуацию, когда сервер сохранил данные, но ответ POST не дошёл.

Код: [AccountingApp.tsx](../../frontend/src/components/AccountingApp.tsx), строки 100, 125 и обработчик формы. Диагностика: `successful_write_failed_reload`, `retry_after_failed_reload`.

### F05 · P1 · Ручной ввод допускает некорректные значения и расхождение со старым учётом

**Воспроизведено через API.**

- Сопровождение с `units: "1.5"` сохраняется: новый журнал показывает 1,50 и 750 ₽, а зеркальная `CompanionEntry` — количество 1. `sync_legacy` обрезает дробную часть через `int(record.units)`. Парсер Telegram, напротив, запрещает дробные сопровождения.
- Типовая услуга со способом расчёта `amount` принимает −500 ₽ и получает `review=false`. Проверка положительной суммы в `calculate()` сейчас действует для разовых работ и расходов, но не для такой услуги. При положительном общем итоге счёта эта отрицательная строка может уменьшить начисления без механизма скидок с пояснением.

Исправление: общая серверная валидация для всех каналов ввода; целое количество для сопровождений; положительная готовая стоимость услуги. Отрицательные значения проводить через предусмотренные корректировки счёта.

Код: [engine.py](../../backend/apps/ledger/engine.py), `calculate`, `save_record`, `sync_legacy`; [ingest.py](../../backend/apps/ledger/ingest.py), проверка количества сопровождений. Диагностика: `fractional_companion`, `negative_ready_amount`.

### F06 · P1 · Старый Excel-экспорт интерпретирует пользовательский текст как формулу

**Воспроизведено безопасной строкой `=1+1`.** В новом счёте есть экранирование `safe_text`, однако старый публично доступный через общий API экспорт `/api/shifts/report.xlsx` записывает комментарии и имена непосредственно в ячейки. Комментарий `=1+1` оказался в `E13` листа «Фокус и Фотобар» с типом ячейки `f`, то есть формулой, а не текстом.

Это нарушает целостность экспортируемого текста и оставляет путь для внедрения формул. Выполнение внешних запросов или команд не проверялось и не утверждается.

Исправление: одинаково экранировать все пользовательские текстовые значения в обоих экспортерах; формулы, создаваемые самим приложением для итогов, оставить формулами.

Код: [shifts/reports.py](../../backend/apps/shifts/reports.py), `append_totals` и `generate_month_report`; сравнить с [ledger/billing.py](../../backend/apps/ledger/billing.py), `safe_text`. Диагностика: `legacy_excel_formula`.

### F07 · P1 · Скрипт бэкапа может объявить успех после ошибки pg_dump

**Установлено по коду; фактический бэкап не запускался.** В `sh` с `set -eu` результат `pg_dump | gzip` определяется последним процессом. При падении `pg_dump` успешный `gzip` может создать архив без полноценного дампа. Скрипт затем выполняет очистку старых архивов и печатает успешное завершение.

Исправление: отдельно проверять успешное завершение дампа и сжатия; писать во временный файл, публиковать готовый архив атомарным переименованием, выполнять retention только после успеха. Добавить периодическую проверку восстановления в отдельную базу. Простого наличия `.gz` недостаточно.

Код: [backup-db.sh](../../deploy/backup-db.sh), строки 2, 14–17.

## Остальные подтверждённые ошибки и технические риски

### F08 · P2 · Удаление промежуточной версии счёта ломает дальнейшие замены

**Воспроизведено.** Подтвердить A → B → C, удалить B, подготовить D как замену C. Удаление обнуляет `C.replaces`. При подтверждении D счёт A уже не распознаётся как предок, и сервер отвечает «За этот период уже подтвердили другой счёт. Создайте новую версию», хотя пользователь именно её и создаёт.

Исправление: сохранять независимый идентификатор цепочки версий и непрерывную историю либо при разрешённом удалении аккуратно соединять ссылки с сохранением необходимых сведений. Не полагаться только на удаляемый FK `replaces`.

Код: [billing.py](../../backend/apps/ledger/billing.py), строки 201–210, 253, 271. Диагностика: `delete_middle_invoice_version`.

### F09 · P2 · Изменение формата услуги не проверяет уже существующие тарифы

**Воспроизведено.** Переключение `input_type` почасовой услуги с `time` на `quantity` возвращает 200, хотя у неё остаются три тарифа `hourly`. Проверка совместимости существует только в `Rate.clean()`, поэтому обратное изменение через `Service.clean()` разрушает тот же инвариант.

Аналогично нужно проверять существующие назначения смен сотрудникам и автоначисления при смене формата/периодичности услуги. Их полная матрица не прогонялась.

Исправление: проверять зависимые объекты при изменении услуги; потенциально несовместимые изменения оформлять новой услугой или явным переводом данных.

Код: [models.py](../../backend/apps/ledger/models.py), `Service.clean`, `Rate.clean`, `Accrual.clean`, `EmployeePreference.clean`. Диагностика: `change_service_input_with_hourly_rates`.

### F10 · P2 · Журнал делает лишние запросы и многократно передаёт одну группу

**Измерено.** Для 50 строк одной общей почасовой смены один `GET records` выполняет **105 SQL-запросов** и возвращает **239 053 байта**. Каждая строка повторно получает дневную группу и список всех её участников.

Дополнительно интерфейс каждые 15 секунд запрашивает `bootstrap`, `records` и до 60 пакетов целиком, независимо от текущего раздела. Пакеты включают все строки счетов и доставки. Ошибка любого из трёх запросов блокирует обновление остальных данных.

Исправление: `select_related` для дневного расчёта, `prefetch_related` участников, один экземпляр данных группы в ответе; краткая выдача списка пакетов, отдельная загрузка деталей выбранного пакета; обновлять только данные активного раздела. Индексы и кэш добавлять по измерениям запросов, а не заранее.

Код: [views.py](../../backend/apps/ledger/views.py), `read(records)` и `serialized(Batch)`; [engine.py](../../backend/apps/ledger/engine.py), `record_dict`; [grouping.py](../../backend/apps/ledger/grouping.py), `group_info`; [AccountingApp.tsx](../../frontend/src/components/AccountingApp.tsx), строки 80–100. Диагностика: `journal_query_count`.

### F11 · P2 · Внешняя синхронизация не имеет надёжного захвата задания

**Риск по коду, внешняя система не вызывалась.** `try_sync_once()` выбирает `pending` без блокировки или перевода в `sending`. Вызовы могут идти одновременно из обработчиков сохранения, процесса `sync` и бота. Несколько исполнителей способны отправить одну запись повторно; счётчик попыток также обновляется конкурентно. Внешний контракт не передаёт уникальный ID события outbox, поэтому его способность безопасно поглощать повторы не подтверждена.

Синхронизация из `transaction.on_commit` также удерживает HTTP-обработчик до выполнения сети: до 10 запросов с timeout 10 секунд на один такой callback. Это создаёт условия для долгого ответа после уже совершённой записи и усиливает F04.

Исправление: транзакционный захват задания, явные состояния доставки, ключ идемпотентности события, управляемые повторы и отправка отдельным worker. Нельзя обещать exactly-once без поддержки принимающей стороны.

Код: [sync.py](../../backend/apps/shifts/sync.py), строки 21–67; [engine.py](../../backend/apps/ledger/engine.py), строки 187–190; `queue_after_write` в [shifts/views.py](../../backend/apps/shifts/views.py).

### F12 · P2 · Не все ошибки входных данных превращаются в понятный ответ

**Воспроизведено.** JSON `[]` или `null` в `POST records` вызывает `AttributeError` и HTTP 500. HTTP-запрос с заголовком `Origin: null` вызывает 500 в Next.js: `new URL(origin)` находится вне `try`. Обычный посторонний Origin корректно получает 403; обход доступа здесь не установлен.

Исправление: проверять структуру JSON до обращения к полям; единообразно возвращать 400/422. Разбор Origin выполнять безопасно и отвергать неподдерживаемое значение. Frontend должен обрабатывать и не-JSON ответы, чтобы не показывать техническую ошибку парсера вместо сообщения о проблеме сервера.

Код: [ledger/views.py](../../backend/apps/ledger/views.py), строки 80–95; [route.ts](../../frontend/src/app/api/shifts/[...path]/route.ts), `proxyRequest`; [AccountingApp.tsx](../../frontend/src/components/AccountingApp.tsx), строки 18–22.

### F13 · P2 · PostgreSQL-прогон тестов требует исправлений

**Воспроизведено на PostgreSQL 18.** `test_api_bootstrap_crud_and_summary` сравнивает `"100"` с `"100.00"`. Это дефект проверки представления суммы, а не обнаруженная ошибка арифметики. Нужен единый API-формат денег либо сравнение `Decimal` в тесте.

Поиск кириллицы не проходит на БД с локалью C, но проходит с ICU `ru-RU`. Требуемая локаль не закреплена в инструкции развёртывания. Это зависимость от конфигурации, а не доказательство поломки текущего production.

Первый прогон также не смог удалить тестовую БД: после потоковых тестов осталось два соединения. В `finally` вызывается `close_old_connections()`, который не обязан закрывать ещё пригодные соединения при `CONN_MAX_AGE=60`. Для повторного полного прогона использовалась отдельная ICU-база и `keepdb`; это обход проблемы очистки в аудите, а не её исправление.

Исправление: явно закрывать соединение каждого тестового потока, закрепить PostgreSQL/locale в CI, запускать тесты на той же основной версии, что и production. Отдельного CI workflow в проекте не обнаружено.

Код: [tests.py](../../backend/apps/ledger/tests.py), строки 224, 383–400; [test_shared_concurrency.py](../../backend/apps/ledger/test_shared_concurrency.py), `parallel`.

### F14 · P2 · Финальный Docker-образ frontend не содержит public

**Установлено по Dockerfile.** На этапе runner копируются `.next` и package-файлы, но не `public`. Локальный production-сервер возвращает `/og.png` с HTTP 200, однако этот файл отсутствует в сборке финального образа. Метаданные сайта продолжают ссылаться на него.

Исправление: копировать `public` в runner. Для воспроизводимого запуска также переносить требуемую конфигурацию Next.js. Проверить образ HTTP-запросами после сборки. Отдельно добавить `.next-dev` в `.dockerignore`: сейчас он может попадать в build context и builder.

Код: [frontend/Dockerfile](../../frontend/Dockerfile), строки 23–25; [layout.tsx](../../frontend/src/app/layout.tsx); [frontend/.dockerignore](../../frontend/.dockerignore).

### F15 · P2 · Переименование сотрудника делит его итог на две строки

**Воспроизведено.** Агрегация идёт по паре `employee_id, employee_name`. После переименования один сотрудник появляется в `employee_totals` дважды — со старым и новым именем и отдельными суммами. Интерфейс показывает обе строки в «Начисления команде» без объяснения.

Исправление: группировать начисления по ID сотрудника, показывать выбранное актуальное имя; исторический снимок имени сохранять в деталях записей и подтверждённых файлах. Необозначенных исполнителей учитывать отдельно.

Код: [ledger/views.py](../../backend/apps/ledger/views.py), `employee_totals`; [AccountingApp.tsx](../../frontend/src/components/AccountingApp.tsx), блок «Начисления команде». Диагностика: `employee_name_split`.

## Архитектурная оценка

**Django + PostgreSQL + Next.js подходят этому приложению.** Для небольшого внутреннего сервиса не требуется разбивать систему на микросервисы или переносить её на Sites. Существующая архитектура опирается на Django ORM, PostgreSQL и отдельные процессы бота/начислений; README прямо описывает Docker-развёртывание. Навыки Sites были изучены, но создание или публикация другого сайта не являются частью аудита.

Удачные решения:

- В расчётах используются Decimal и распределение остатка по копейкам; есть тесты общего минимума/максимума смены.
- Снимок дневного тарифа сохраняет существующие суммы до явного пересчёта.
- Подтверждённый счёт содержит снимки строк, получателей и Excel; изменение исходной записи не переписывает уже выданный файл.
- Fingerprint и версия защищают подтверждение счёта и применение предпросмотра пересчёта от изменившихся данных.
- Telegram update дедуплицируется, редактирование нескольких частей сообщения транзакционно.
- Доставка имеет очередь, отдельные состояния неопределённого результата и защищённый ручной повтор.
- Миграции сохраняют прежние суммы и ссылки на историю; есть отдельные миграционные проверки.
- Фильтрация журнала выполняется до пагинации и подсчёта итогов.
- В Compose наружу опубликован Caddy; backend и frontend не имеют host-портов. Basic Auth — осознанная граница доступа для внутреннего инструмента.

Что нужно укрепить:

1. **Единая точка изменения учёта.** Сейчас она заявлена в `commit_records`, но обходится стандартным Admin; часть проверок отдельно живёт в парсере и API. Общие инварианты должны применяться ко всем каналам.
2. **Старый и новый учёт.** Мост через Django signals усложняет порядок сохранений, аудит и синхронизацию. Сохранить совместимость разумно, но зафиксировать, что `ledger` является источником истины, и сделать запись в legacy явным адаптером. Не развивать параллельно независимые правила тарифов старого API.
3. **Блокировки.** Singleton `Settings` сериализует все изменения, включая формирование Excel и регулярные начисления. Это простой рабочий подход для малого числа пользователей; его пропускная способность ограничена. Сначала убрать сеть из HTTP-ответов и лишние запросы, затем измерить необходимость более узких блокировок. Не заменять блокировки без сохранения инвариантов счетов и смен.
4. **Рост истории.** `is_frozen` сканирует JSON строк всех подтверждённых счетов; регулярное начисление каждый раз проходит даты от начала расписания; чтение пакетов загружает полные снимки. При росте данных полезны отдельная индексируемая связь записи со счётом, курсор начисления и краткий API списка пакетов.
5. **Границы модулей frontend.** Основные разделы, универсальные формы, загрузка, расчётные представления и действия сосредоточены в `AccountingApp.tsx`. Тип `Item` допускает произвольные `any`; TypeScript не проверяет полноценный контракт API. Выделить модули по пользовательским разделам и типизированные DTO, не переписывая всё приложение.
6. **Пользователи и аудит.** Basic Auth достаточно для одного доверенного оператора. При нескольких операторах `actor="web"` не даёт персональной ответственности и в API нет разграничения прав. Утверждающий по Telegram ID проверяется; подтверждение на сайте доступно оператору с общим доступом. Это нужно согласовать как продуктовую модель, прежде чем добавлять роли.
7. **Настройки production.** `check --deploy` на локальных значениях выдал шесть предупреждений: DEBUG, слабый запасной SECRET_KEY, secure cookies, HTTPS redirect и HSTS. Это не доказательство таких настроек на сервере: часть HTTPS обеспечивает Caddy. Однако `SESSION_COOKIE_SECURE` и `CSRF_COOKIE_SECURE` не настроены в коде, а отсутствие переменных позволяет стартовать с DEBUG и известным dev-ключом. Нужны явные production-настройки и отказ запуска с dev-секретом. `AUTH_PASSWORD_VALIDATORS` пуст.
8. **Эксплуатация.** Healthcheck Django возвращает `ok` без обращения к БД. У worker нет видимого heartbeat, у backend/frontend в Compose нет проверок здоровья. Python-зависимости заданы диапазонами без lock-файла. Для воспроизводимости и диагностики нужны закреплённые версии, проверка готовности БД, контроль последнего цикла worker и проверяемый backup/restore.

## Как повторить диагностику

Из корня проекта:

```powershell
.venv/Scripts/python.exe audit/2026-09-12/probe_backend.py
node audit/2026-09-12/probe_frontend.cjs
```

Первый сценарий сам создаёт БД в памяти, применяет миграции и откатывает каждый блок; второй использует React test renderer и имитацию сети. Они печатают наблюдения, а не являются готовыми регрессионными тестами с утверждением правильного поведения.

Результаты: [backend-results.jsonl](backend-results.jsonl), [frontend-results.jsonl](frontend-results.jsonl).

[probe_http.cjs](probe_http.cjs) проверяет реальный HTTP и **изменяет данные**. Он предназначен только для отдельно подготовленного тестового приложения на `127.0.0.1:3100`; не запускать против рабочей базы. Во время аудита использовался собственный Django на `127.0.0.1:8100` с SQLite-файлом в игнорируемом каталоге `backups/audit-2026-09-12` и выключенными внешними интеграциями.

Обычный серверный прогон:

```powershell
cd backend
../.venv/Scripts/python.exe manage.py test apps.ledger apps.shifts --noinput
../.venv/Scripts/python.exe manage.py check
../.venv/Scripts/python.exe manage.py makemigrations --check --dry-run
```

Тесты PostgreSQL запускать с отдельными тестовыми реквизитами и учётом F13. Наличие зелёного SQLite-прогона не заменяет проверку PostgreSQL.
